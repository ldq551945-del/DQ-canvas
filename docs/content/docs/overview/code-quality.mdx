# 代码质量分类

本文按职责、业务风险和验证成本对代码分类，不把目录简单评成“好”或“坏”。分类用于决定修改前要读什么、需要跑哪些测试，以及哪些区域必须渐进治理。

## 当前基线

截至 2026-08-06，`web/src` 约有 1289 个 TypeScript、TSX 与 CSS 文件、17.9 万行代码；其中 409 个同域测试文件。75 个文件超过 500 行，21 个文件超过 800 行，说明项目已有较完整的自动化基础，但复杂度集中在少数核心入口。

本轮本地基线结果：

| 检查 | 结果 |
| --- | --- |
| Web TypeScript | `pnpm run typecheck` 通过 |
| Web 单元与契约测试 | 413 个文件、1858 项测试通过；1 个文件、2 项测试跳过 |
| Web 格式与生产构建 | Prettier 通过；Next.js 生产构建通过并生成 62 个静态页面 |
| 文档站 | 类型检查通过；生产构建通过并生成 37 个页面 |
| rembg sidecar | Python 3.12 下 37 项单元测试通过 |
| 部署契约 | 6 套 Compose 可解析；Compose 专项 13 项测试通过 |
| 依赖审计 | Web 与 Docs 均未发现中危及以上已知漏洞 |

本轮在本机 Node.js 24.16.0 下使用仓库统一的 pnpm 10.34.5 完成冻结安装与全部检查；仓库 CI 使用 Node.js 22 与同版 pnpm。GitHub Actions 的通过结果仍是合并与发布前的最终环境证据。

| P4 文档与状态区 | `README.md`、`docs/content/docs/`、`CHANGELOG.md`、`VERSION` | 项目定位、功能、部署、接口、待验收状态和版本信息 | 是外部契约的一部分，必须与代码一致 | 已实现但未真实验收的能力写入“待测试”；不得把本地自动化通过写成生产可用承诺 |

## 新增能力归类

- Canvas 性能模式、组件菜单、资源引用、任务面板、连线插入、编组与节点锁定属于 P1 画布编排。
- 标注、情绪、人物质感、多视角和媒体替换属于 P1 图片节点工具；参数生成与蒙版规则应保留在同域纯函数。
- rembg 请求校验、持久任务、全局单推理队列、取消与结果登记属于 P0 任务/媒体保护区；`services/rembg/` 是内部执行 sidecar，不对公网开放。
- MediaPipe、FaceCap、Three.js Basis 与浏览器 WASM/模型文件属于 P3 第三方资源，来源和许可证记录在 `NOTICE`。

## 治理顺序

1. 先守住 P0 的身份、归属、幂等、事务、取消和媒体清理不变量。
2. 新需求触及 P1 超长入口时，先抽出明确职责，再增加功能分支。
3. 逐步补齐与 Next.js 16、React 19 兼容的 ESLint 和浏览器 E2E 基线。
4. 真实模型、支付、对象存储、多实例恢复和低内存部署继续按[待测试](/docs/progress/pending-test)记录，不用本地 mock 代替生产验收。
