# 低内存服务器部署

低内存机器不要现场执行 `next build` 或 `docker build`。`docker-compose.lowmem.yml` 只运行 DQ-绘图应用和生成 Worker，PostgreSQL 使用外部托管服务或另一台服务器；抠图 sidecar 也必须部署在另一台有余量的主机，或使用已经运行的内部 rembg 服务。

## 最低资源边界

建议整台服务器至少提供：

- 1 vCPU。
- 1GB 物理内存和至少 1GB swap。
- 10GB SSD 可用空间。
- 64 位 Linux、Docker Engine 与 Compose v2。
- 外部 PostgreSQL 16 和外部 S3/OSS，避免数据库与长期媒体继续占用这台低内存服务器。
- HTTPS 域名，以及能够访问模型、数据库、对象存储和 SMTP 的出站网络。

应用容器本身限制为 512MB，但宿主机还需要给 Linux、Docker、Nginx/宝塔和文件缓存保留内存，因此不建议购买只有 512MB 物理内存的服务器。该模式适合安装体验、个人低频使用和少量并发，不适合在本机执行 Docker 构建、长视频转码或短剧整集合成。

## 配置

```bash
cp .env.example .env
```

至少修改：

```dotenv
NEXT_PUBLIC_SITE_URL=https://store.dqin-666zj.top
DATABASE_URL=postgres://user:password@database-host:5432/dq
DQ_DATABASE_SSL=1
DQ_DATABASE_POOL_MAX=5
DQ_ENCRYPTION_KEY=replace-with-a-long-random-secret
# 仅填写内网或 VPN 地址，不要暴露给浏览器或公网
DQ_REMBG_URL=http://rembg.internal:7000
DQ_REMBG_INTERNAL_TOKEN=replace-with-a-long-random-token
```

`DQ_REMBG_URL` 是低内存 Compose 的必填项。远端服务应提供与默认 sidecar 相同的
`GET /livez`、`GET /readyz` 和 `POST /v1/remove` 契约，并在服务端校验
`Authorization: Bearer <DQ_REMBG_INTERNAL_TOKEN>`。跨主机链路建议走私有网络或
VPN；不要把 `7000` 端口发布到互联网，也不要让浏览器直接调用该地址。
外部服务的 `/readyz` 应报告与画布 V3 一致的模型白名单：`u2net`、
`isnet-general-use`、`u2net_human_seg`、`isnet-anime`、`silueta`。这些权重需要预先
下载并校验；不要让用户任务在推理超时窗口内临时下载模型。

## 启动

```bash
docker compose -f docker-compose.lowmem.yml pull
docker compose -f docker-compose.lowmem.yml up -d
```

该配置限制应用容器：

- 512MB 内存。
- 768MB 内存与 swap 总上限。
- Node.js 堆内存 384MB。
- 线程池大小 2。

建议保留 512MB 到 1GB swap。PostgreSQL 和 rembg 模型服务可以放在外部，但应用服务器仍需挂载 `DQ_DATA_DIR` 以保存图片、视频和音频。远端 rembg 主机建议至少 2 vCPU、5 GB 可用内存，并为五个画布白名单权重及推理工作内存预留磁盘和内存；不要把这部分资源计入低内存应用容器的 512MB 限额。远端 sidecar 应保持单推理槽、计算线程 2、ONNX inter-op 线程 1，并在模型入口限制最长边 2048px。

如果已启用 S3/OSS，新媒体不会保留本地持久副本，但 FFmpeg、视频下载和格式规范化仍可能使用临时磁盘。需要稳定使用图片/视频工作台时建议升级到 2 vCPU / 2GB；需要短剧合成时建议至少 4 vCPU / 8GB。
