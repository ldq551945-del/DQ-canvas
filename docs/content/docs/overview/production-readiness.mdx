# 生产上线基线

应用代码可以提供稳定能力，但商业上线还依赖部署环境、支付商账号、监控平台和运营主体。宝塔、Docker、云容器和托管 PostgreSQL 使用同一检查标准。

## 当前验收证据边界

- Web 全量自动化、Prettier、TypeScript、发布检查与生产构建已通过；Docs 的类型、索引和生产构建也已通过。真实 PostgreSQL 已覆盖社区点赞、关注、拉黑和事务回滚，但未替代多账号人工操作与生产并发。
- 当前真实渠道只确认文本最小调用成功。图片健康请求虽然返回 HTTP `200`，仍缺实际图片结果留档；视频和音频逻辑模型未配置，不能声明对应生成链路通过真实上游验收。
- Compose 与 Render 配置已通过 YAML 解析，但本机没有 Docker CLI，尚未执行 `docker compose config`、镜像构建、容器启动、宝塔安装或干净 Linux 恢复验证。
- 浏览器前序回归已覆盖主要桌面、390px/430px 和浅深主题页面；本轮内置浏览器受本地地址策略限制，未补充新的移动端截图。生产发布仍需按目标浏览器、真实账号和真实媒体完成最终人工验收。

## 健康检查

- `GET /api/health/live`：只检查 Web 进程是否能响应，Docker Compose 使用该地址，避免数据库短暂异常导致应用容器反复重启。
- `GET /api/health/ready`：检查数据库连接、表结构、加密密钥和首个管理员；未完成安装或依赖异常时返回 HTTP `503`，用于反向代理、负载均衡和外部监控。
- `/api/install/status`：面向安装页面的安全状态，不应作为生产告警依据。

## 计划任务

配置至少 32 个字符的 `VOZEB_PRO_MAINTENANCE_TOKEN`，每 5 分钟调用：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer $VOZEB_PRO_MAINTENANCE_TOKEN" \
  https://vozeb-pro.example.com/api/maintenance/billing-orders/expire
```

宝塔使用计划任务，Docker 使用宿主机 Cron，云平台使用 Scheduler。任务可以重复执行，多实例会通过数据库锁避免重复关闭订单。

## 备份与恢复

- 后台“数据备份”导出脱敏业务数据，用于跨 Provider 恢复账号权益、非敏感设置、公共提示词和生成记录。
- PostgreSQL 使用数据库平台或 `pg_dump` 做整库备份；支付流水、支付配置和密钥不依赖业务 JSON 备份。
- 本地媒体目录、S3/OSS 对象和对象存储配置分别备份；不要只备份数据库后假设媒体能够恢复。
- 至少保留每日自动备份、异地副本和定期恢复演练。备份任务成功不等于恢复可用。

## 监控与告警

根据部署环境选择 Sentry、OpenTelemetry、云厂商 APM、Prometheus/Grafana 或日志平台，不要求所有部署同时安装同一套组件。上线前至少覆盖：

- `/api/health/ready` 可用率和连续失败。
- Web CPU、内存、磁盘、容器重启和媒体容量。
- PostgreSQL 当前连接数、连接池等待、慢查询、锁等待和存储增长。
- API P50/P95/P99、HTTP 5xx、登录失败率和限流触发量。
- 图片、视频、音频和 Agent 的成功率、耗时、退款率和渠道冷却次数。
- 支付下单成功率、回调处理失败、长时间待支付订单和退款失败。

服务器日志可能包含内部错误细节，应限制管理员访问并设置保留周期；密钥、支付凭据、登录令牌和媒体签名参数不得写入日志平台。

私有媒体已按用户归属或绑定资源/用途/过期时间的短期签名读取，公开作品媒体每次重新校验当前公开版本；本地与代理 Range、HEAD、条件缓存、分层限流和进程内并发回收已有自动化证据。真实代理跳数、多实例限流、私有 S3、热点资源、文件句柄与外网下行仍必须在生产等价环境压测，代码上限不能替代容量和账单证据。

## 支付验收

每个真实启用的支付商都必须在沙箱或生产前测试：下单、成功支付、失败支付、重复/乱序/延迟回调、订单超时、全额退款、退款失败恢复和账单对账。支付宝若选择官方支付，需要验证电脑网站收银台跳转与同步/异步返回；若选择当面付，需要单独验证 `precreate` 二维码、扫码支付、二维码过期和异步通知，不能用官方支付测试代替当面付证据。当前自动退款按整笔订单处理；如果实际业务需要部分退款，必须先补齐订单、支付流水、积分回收和会计口径，再进行支付商部分退款验收。代码支持某个渠道不代表该商户账号、证书、回调域名和退款权限已经通过验证。

代码已锁定订单支付渠道，并在回调幂等处理前校验标准化渠道、订单金额和币种；已支付订单收到不同交易会进入冲突核对，而不是静默视为重复。正式验收仍要保存每个支付商的正常、重复、乱序、迟到、金额篡改、币种不符和跨渠道回调证据，并明确人工核对与补账责任人。

限时促销和单张优惠券已保存服务端价格快照，并接入锁券、释放、核销和整单退款关联。正式启用前仍必须使用生产等价 PostgreSQL 验证并发领券、同券并发下单、自动超时、迟到支付冲突和重复回调，并逐个支付商核对实收、退款及对账金额都等于订单 `amountCents`；自动化规则测试不能替代这些证据。

单层邀请奖励已接入注册、首笔可信实付、冷静期结算和整单退款事务，并提供网络/支付身份哈希风险信号与后台人工处置。正式启用前仍必须用真实 PostgreSQL、多个账号和实际支付回调验证原子绑定、重复事件、并发结算、月度/活动上限、维护调度、积分反向流水及优惠券撤销冲突；同时由运营确定风控阈值、冻结通知、申诉与误伤恢复流程。单一 IP 信号不能作为自动认定欺诈的唯一依据。

## 容量与压测

先以生产相同数据库、代理和存储进行 100、500、1000 并发分级测试，记录登录、列表、生成任务创建、SSE 连接、支付和后台查询的 P95/P99。根据瓶颈再调整 `VOZEB_PRO_DATABASE_POOL_MAX`、实例数、队列或缓存，不要仅靠增大连接池解决并发问题。

后台财务摘要已使用单次 PostgreSQL 聚合和订单/支付流水时间索引，且正常退款不再进入支付状态异常计数；这只能证明查询与口径基础，仍需在生产等价订单量下保存执行计划、P50/P95、连接池等待和真实支付商对账证据。

短剧成本概览已改为按用户、项目、任务类型和状态在 PostgreSQL 聚合，并增加项目定向索引；该改动只减少无界任务 JSON 读取，仍需在生产等价短剧任务规模下记录执行计划、P50/P95、连接池等待和成本账本核对结果。

## 异步生成与计费闭环

图片、视频、音频和 Agent 任务需要在真实渠道下验证排队、超时、取消、重试、断线恢复、重复提交和卡死任务接管。每个任务都应能与原消费流水、失败退款、用户余额、生成记录和媒体登记逐项核对；重启和多实例竞争不能造成重复扣费、重复资产或“任务失败但积分未退”。

混合模型渠道可以按模型保存 OpenAI、Gemini、Seedance 2.0 或兼容协议与创建/查询路径，但代码适配不能替代供应商文档和真实密钥验收。上线前应逐渠道保存实际模型目录响应、分页证据及文本/图片/视频最小调用结果；上游未公开目录或使用不透明模型名时，必须由管理员维护模型能力与路由，不能把名称猜测当成生产证据。

PostgreSQL 在线扣费已使用定向的用户、套餐、每日钱包、额度和流水查询，完整认证快照只保留给备份或兼容路径。该优化只说明高频查询边界更清晰，仍必须通过真实生成并发、锁等待、超时退款和余额对账验收，并明确最大重试次数、人工补账责任和上游不可用时的暂停/降级规则。

## 安全事件与数据泄露响应

商业上线前需要单独准备并演练安全事件响应手册，不能把它拆散在“密钥加密”和“日志监控”两项里：

- 针对模型密钥、支付证书、维护令牌、OSS 凭据、Session 和个人数据泄露，明确发现、分级、隔离、吊销、轮换、取证、修复、用户通知和复盘责任人。
- 覆盖异常登录、越权访问、私有媒体暴露、数据库泄露和支付数据异常，保留必要证据，并按运营地区和合同要求判断是否需要通知用户、支付商、供应商或监管机构。
- 演练暂停受影响模型/支付渠道、撤销会话、轮换密钥、恢复备份和重新验证媒体及订单引用；不能因为处置事件而静默损坏生成记录、积分或财务数据。
- 依赖扫描、加密存储和已有健康探针只能作为技术基础，不能替代可执行的事件响应、通知和恢复证据。

## 法律与运营

站内 `/privacy` 和 `/terms` 只是产品级基础页面。正式运营前，必须由法律顾问按运营主体、服务地区、数据存储位置、第三方模型服务、退款规则、知识产权、内容审核和用户注销流程进行审核并替换为正式版本。面向中国大陆、欧盟或其他地区时分别核对当地适用法规。

登录用户可在个人中心导出自己的账户、积分、账务摘要、创作记录和注销申请 JSON；导出不会包含媒体二进制、密码、会话、API 凭据、支付原始载荷、临时签名 URL 或平台内部规划详情。该能力只覆盖基础数据访问权，不能代替正式的数据请求处理制度。

个人中心支持通过当前密码复核提交和撤回注销申请；后台“注销申请”一级页面支持管理员受理或拒绝，处理备注必填并写入审计记录。受理只代表进入线下身份复核和数据保留核对，不会自动停用账号或删除订单、创作数据与媒体。该闭环属于注销申请管理，不等于已经完成正式注销执行。

仍需确认注册时的协议同意方式、协议版本和同意时间是否留痕；明确注销正式执行、创作数据删除与订单/支付法定保留之间的边界，并建立身份复核、响应时限和处置制度。第三方模型、支付、SMTP 和对象存储服务的数据处理与跨境传输情况应在正式政策中披露。

## 内容、客服与财务

- 作品发布已具备草稿、版本审核、稳定分享、公开广场、公开创作者主页、精选、举报、下架申诉、审计记录和动态媒体授权；用户或管理员先下架再永久删除时只清空发布快照、治理和互动记录，源素材、项目与媒体文件保持不变。当前用户公开界面只提供点赞/取消与作者关注，作品收藏、评论和评论举报的 UI、API、服务、计数、Schema 与后台治理均已移除；本人关注、粉丝和点赞历史按登录用户分页读取，并支持取关、取消点赞和拉黑，拉黑会解除双方关注并阻止再次关注。公开主页只展示资料身份公开作品与聚合统计，不公开邮箱、内部用户 ID 或关系名单。互动通知继续保留，7/30 天榜单只按有效点赞、精选和新鲜度执行基础反刷新账号过滤。默认人工审核，也可接入关键词或中立 HTTP 风险信号，但自动结果不会直接公开。这些代码能力不等于平台内容合规或反刷运营已经闭环，仍需用真实多账号验证关系隐私、拉黑/取消拉黑、下架/封禁联动，并完成侵权投诉、刷量规则、人工值班、处置时限、误伤复核、隐私规则、生产监控和真实演练证据。
- 短剧工作台的“内容审核”是用户确认剧本事实的生产 Gate，不是平台内容合规审核。正式运营仍需由平台举报/申诉流程、人工复审制度和审计证据承接。
- 需要明确年龄限制、禁止用途、AI 生成内容标识、用户上传内容授权、侵权投诉和下架流程；用户不能默认对输入素材或生成结果拥有不受限制的商业权利。
- 帮助中心和公告不能代替客服流程。至少明确客服入口、服务时间、支付问题、内容举报、隐私请求和投诉升级方式。
- 当前支持 CSV 支付账单导入与差异对账；正式运营仍需明确账单获取周期、异常处理责任、退款审批、发票/税务和财务留档规则。

## 供应商与安全治理

- 为模型渠道、支付商、SMTP、对象存储和通知服务建立供应商清单，记录价格、配额、数据使用、数据区域、保留期限、SLA、停服通知和替代渠道。代码支持某个 Provider 不等于供应商合同、商户权限和退款权限已经完成。
- 在用户协议中说明用户内容授权、生成内容权属不确定性、第三方模型训练/留存边界、品牌和人物素材授权责任，以及上游模型变更导致的结果差异。
- 落实 AGPL-3.0、第三方依赖、字体和素材许可证义务，保留许可证与版权声明；正式发布前完成依赖、容器镜像和密钥泄露扫描，并建立漏洞披露、修复和安全公告流程。
- 明确模型渠道故障、价格调整、配额耗尽、模型下线和内容安全服务不可用时的降级、暂停生成、用户通知和退款规则。

## 账户风控与商业经营缺口

下面事项不能由应用代码或宝塔面板自动完成，正式商业上线前必须由运营、财务、法律和技术负责人共同确认：

- **经营主体与资质**：确认运营主体、服务地区、域名与网络相关资质、支付商户资质、发票/税务主体及第三方模型、SMTP、支付和对象存储的合同与数据处理边界。AGPL-3.0 的网络服务开源义务仍需按实际二次开发和交付方式履行。
- **计价与成本**：固定积分与套餐的兑换口径，区分一次性积分、套餐每日积分和过期规则；建立模型调用、失败退款、存储、带宽、支付手续费和税费的成本表，设置上游余额、异常成本和毛利预警。当前经营看板不能直接当作利润报表。
- **权限与审计**：当前后台只有普通用户/管理员两类角色，尚未提供财务、客服、内容审核、运营和只读审计等细粒度职责。正式团队运营前应确定最小权限、退款/积分调整复核和高风险操作审批规则。
- **事故与服务**：明确版本发布、回滚、值班、故障分级、状态通知、客服入口、响应时限和升级路径。健康探针、日志和告警是技术基础，不等于已经建立 SLA 或人工响应流程。
- **规模与增长**：定义注册、首个成功作品、生成成功率、付费转化、留存、ARPU、复购、退款率和单位作品成本的统计口径，再据此调整套餐升级、续费、优惠、邀请奖励参数和批量运营能力；当前邀请漏斗不能替代完整经营分析。
- **账户与滥用治理**：明确年龄门槛、地区限制、可接受使用政策、批量注册/刷积分/盗用支付/自动化滥用指标，以及冻结、解冻、申诉和误伤复核流程。
- **供应商退出与可迁移性**：为模型、支付、SMTP、对象存储和通知服务保留停服、封号、涨价、配额耗尽和跨境政策变化时的替代与数据导出方案，确保账号、订单、媒体和用户数据不会被单一供应商锁死。

## 容易遗漏的上线控制项

以下事项经常不在“功能已完成”清单中，但会直接影响商业上线后的安全、成本和售后责任：

- **管理员高风险保护**：确认管理员是否需要 MFA、登录设备/异常 IP 告警、短会话和高风险操作二次确认；在细粒度角色上线前，至少限制管理员账号数量并定期复核权限。
- **密钥生命周期**：建立加密密钥、模型密钥、支付证书、维护令牌和 OSS 凭据的创建、保管、轮换、吊销和泄露应急流程；恢复备份时必须同时验证密钥可用性，不能只恢复数据库和媒体。
- **支付争议**：除退款外，明确拒付、支付争议、重复扣款、退款原路退回失败和支付商冻结账户的处理责任、证据留存及用户通知。
- **数据生命周期**：为对话、生成任务、原始媒体、WebP 变体、临时文件、审计日志、支付记录和 S3 对象定义保留期限、删除触发条件、法律保留例外、生命周期清理和删除结果核验。
- **存储与网络成本**：按本地磁盘、OSS 请求、存储容量、外网下行、CDN/代理和备份副本建立成本监控，设置容量、带宽和对象存储账单预警；S3 开关本身不等于成本治理。
- **故障沟通**：准备状态页或公告替代方案、维护通知模板、生成失败/退款延迟/上游停服的用户文案和客服升级路径，明确谁有权暂停某个模型或支付渠道。
- **无障碍与浏览器支持**：在目标浏览器和移动端完成键盘操作、焦点顺序、表单错误、对比度、动态状态播报、媒体替代文本和下载行为验收，并公布最低支持范围。
- **通知可达性**：验证注册、验证码、密码重置、支付结果和故障通知的实际送达；配置发信域名 SPF/DKIM/DMARC，监控退信与投诉，保留模板版本，并为通知供应商故障准备人工或站内公告兜底。
- **环境与回滚**：开发、预发布和生产必须隔离数据库、对象存储桶、支付商户、模型密钥、维护令牌和回调域名；每次发布都要有迁移前备份、冒烟检查、可替换镜像和回滚后数据兼容记录。
- **成本熔断**：在单用户、单任务、单日和全站维度设置模型调用、媒体处理、存储与外网下行上限；积分余额校验不能代替上游配额、盗号和异常成本保护。
- **商业证据**：每项 P0/P1 控制项都应登记负责人、截止时间、环境、证据链接、复核人和复核日期；没有真实支付、通知、恢复、压测或安全演练证据时，仍标记为未完成。

这些控制项应落到负责人、截止时间、证据链接和复核结果；没有证据时继续标记为未完成，不要因为已有接口、后台开关或自动化测试就视为商业闭环。

### 上线判定

1. 任一阻断项没有负责人、复核人和真实证据时，只能进入内部或封闭测试，不能宣称正式商业上线。
2. 代码测试、健康探针、后台开关和配置页面只能证明技术基础，不能替代支付商、OSS、邮件、代理、恢复和人工流程验收。
3. 灰度期间每周复核生成成功率、退款率、单位作品成本、存储增长、投诉和供应商异常；发现资金、隐私或内容安全风险时立即暂停对应渠道并保留用户数据与财务记录。
